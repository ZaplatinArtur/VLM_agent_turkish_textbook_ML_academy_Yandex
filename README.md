## Введение

Современная мультимодальная языковая модель умеет читать условие со снимка и
решать многие школьные задания без внешней помощи. Однако часть вопросов требует
точных определений, формулировок или способов решения из конкретного учебника.
В таком случае агенту необходимо не просто выполнить поиск, а определить,
нужен ли он вообще, выбрать подходящий источник и не позволить найденному
контексту исказить факты с исходного изображения.

| Элемент исследования | Формулировка |
| --- | --- |
| **Объект** | решение школьных заданий на турецком языке мультимодальным агентом |
| **Предмет** | влияние источника знаний и стратегии вызова инструментов на качество ответа |
| **Цель** | определить, когда поиск по учебникам улучшает ответы по сравнению с той же моделью без инструментов и с веб-поиском |

> **Исследовательский вопрос:** повышает ли поиск по учебникам качество ответов
> по сравнению с той же моделью без инструментов и с веб-поиском?

### Проверяемые гипотезы

1. Веб-поиск полезнее для общих и редких фактов, которые могут отсутствовать во
   внутренних знаниях модели.
2. Поиск по учебникам полезнее для заданий, зависящих от конкретной программы,
   терминологии, формулировок и разобранных примеров.
3. Принудительный поиск ухудшает часть самодостаточных задач на вычисление и
   рассуждение, поскольку добавляет нерелевантный контекст.
4. Маршрутизация по типу задания и проверка релевантности найденных фрагментов
   должны быть эффективнее безусловного вызова одного инструмента.

### Используемые подходы

- **Контролируемое сравнение:** одна модель решает одинаковые задания без
  инструментов, с веб-поиском и с поиском по учебникам.
- **Гибридный поиск по учебникам:** лексический и векторный поиск объединяются,
  после чего кандидаты проходят повторное ранжирование и порог релевантности.
- **Агент с приоритетом изображения:** условие на изображении остаётся главным
  источником; поиск вызывается не более двух раз, допускается одна
  переформулировка запроса, а противоречащие фрагменты отбрасываются.
- **Маршрутизация по источникам:** точное совпадение с официальным источником
  обрабатывается отдельно, при неуверенности управление передаётся агенту.
- **Единая оценка:** режимы сравниваются попарно на совпадающих заданиях с
  помощью точных метрик, мультимодального судьи и анализа исправленных и
  ухудшенных ответов.

## Ход работы

| Этап | Что сделано | Результат |
| --- | --- | --- |
| 1. Контракты и данные | Зафиксированы общие схемы задания, изображения, найденного фрагмента и результата агента | Все компоненты обмениваются данными в едином формате |
| 2. Базовая линия | Реализован запуск модели без инструментов и подготовлены воспроизводимые выборки | Получена точка отсчёта для всех последующих сравнений |
| 3. Внешний поиск | Проведён прогон с веб-поиском на том же наборе заданий | Измерено влияние широкого внешнего источника на разные типы вопросов |
| 4. Корпус учебников | Учебники разобраны на текстовые и визуальные единицы, построены поисковые индексы | Поиск возвращает фрагменты с предметом, классом, страницей и оценкой релевантности |
| 5. Поиск и повторное ранжирование | Добавлены гибридное извлечение, объединение выдачи, повторное ранжирование и отсечение слабых результатов | Агент получает компактный проверенный контекст вместо необработанного списка кандидатов |
| 6. Агентная стратегия | Реализованы прямой вызов инструмента, приоритет исходного изображения, ограничение числа поисков и переформулировка запроса | В журнале сохраняются запросы, релевантность, конфликты и причина завершения |
| 7. Оценка и анализ | Созданы единый судья, предметные срезы, попарное сравнение и интерфейс просмотра ошибок | Можно видеть общую точность, исправленные и ухудшенные ответы и влияние использования поиска |
| 8. Текущий этап | Сравниваются профили поиска и правила маршрутизации на замороженных выборках | Цель — определить, каким задачам действительно нужен веб, учебник или решение без инструментов |

Контракты данных, правила оценки и устройство поискового инструмента подробно
описаны в [`docs/data_contract.md`](docs/data_contract.md),
[`docs/evaluation_protocol.md`](docs/evaluation_protocol.md) и
[`docs/retrieval_tool_contract.md`](docs/retrieval_tool_contract.md).

## Результаты: без инструментов и веб-поиск

На едином срезе из **8300 школьных заданий** модель Qwen3.5-9B без
инструментов получила **84,1%**, а агент с веб-поиском — **81,8%**. Итоговая
разница составила **−2,4 п.п.**; поиск использовался в 53% заданий.

| Тип вопроса | Без инструментов | С веб-поиском | Разница |
| --- | ---: | ---: | ---: |
| Закрытый, 5560 заданий | 82,1% | 81,5% | −0,6 п.п. |
| Открытый, 2740 заданий | 88,2% | 82,2% | −6,0 п.п. |

Веб-поиск почти не изменил качество закрытых вопросов, но заметно ухудшил
открытые задачи, где ответ требуется вывести рассуждением. Это указывает на
необходимость маршрутизации: подключать поиск для задач на знание фактов и не
показывать инструмент модели там, где важнее самостоятельное решение.

Метрика — Exact Match; условия сравнивались на одинаковых заданиях без ошибок
в обоих прогонах. [Полный интерактивный отчёт](https://claude.ai/code/artifact/cefe767d-3f81-459e-b90a-d388b3e4e039)
содержит разрезы по языкам, предметам, формату задания и факту вызова поиска.

> **Основной вывод.** Внешний поиск полезен только тогда, когда источник
> соответствует типу задачи. Веб-поиск лучше подходит для общих и редких фактов
> благодаря широкому охвату, а textbook RAG потенциально полезен для знаний,
> формулировок и способов решения, специфичных для конкретных учебников. Если вся
> необходимая информация уже содержится на изображении и требуется рассуждение,
> принудительный поиск может добавить шум и ухудшить ответ. Поэтому агент должен
> сначала определить тип задачи и обращаться к подходящему источнику только при
> нехватке информации.

## Быстрый старт

Требуется Python 3.11 или новее. Для локального dry-run не нужны GPU и
запущенная модель.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[sources,dev]"

.\.venv\Scripts\python.exe -m mla_baseline.runner `
  --tasks data/eval/tasks.sample.jsonl `
  --condition b0_no_tools `
  --dry-run
```

Подробная установка, настройка inference backend и сценарии запуска:
[`docs/getting-started.md`](docs/getting-started.md).

## Система за минуту

<p align="center">
  <img src="docs/assets/pipeline-overview-v5.png" alt="Задание, проверка официального источника, агент с поиском по учебникам, результат и единая оценка" width="100%">
</p>

1. `agent_rag_sourced` передаёт роутеру только наблюдаемый текст задачи.
   Точная привязка возвращает ответ из официального ключа; любая неуверенность
   заканчивается `abstain`.
2. После `abstain` image-first `AgentRag` решает задачу сам или делает не более
   двух различных вызовов `textbook_search`. Полученные сведения проверяются на
   конфликт с исходным изображением.
3. Все ветки формируют единый `SolveResult`. Эталон добавляется только в judge
   adapter, поэтому solver его не видит.

<details>
<summary><strong>Подробности поиска и его профилей</strong></summary>

По умолчанию `textbook_search` напрямую вызывает профиль
`rrf_e5-small_bm25_cross-encoder`: Turkish BM25 и multilingual E5-small
объединяются через RRF, затем кандидаты переранжируются BGE cross-encoder с
LoRA-адаптером. Слабая выдача скрывается от агента. Дополнительно доступны
`advanced` и другие именованные профили через `RETRIEVE_PROFILE`.

</details>

## Multilingual benchmark framework

The repository includes a deterministic evaluation harness for TUMLU (9 Turkic
languages), EXAMS-V (13 languages with exam screenshots), and MGSM (11
languages with open numeric answers). See
[`docs/mlbench_framework.md`](docs/mlbench_framework.md), the frozen slices in
`data/mlbench/bench300/`, and the baseline report in
`reports/mlbench300_summary.md`.

## Что сравниваем

| Режим | Условие runner | Доступные данные и инструменты |
| --- | --- | --- |
| 🧠 Без инструментов | `b0_no_tools` | исходный текст или изображение задачи |
| 🌐 Веб-поиск | `b1_search` | задача и ограниченный инструмент веб-поиска |
| 📚 Textbook RAG | `agent_rag` | задача и checked retrieval по учебникам |
| 🔎 Source-aware RAG | `agent_rag_sourced` | fail-closed роутер, затем fallback в `agent_rag` |

Одинаковый контракт результата позволяет применять один judge и считать paired
`fixed/regressed` на совпадающих `task_id`. Числа из разных датасетов, моделей,
prompt versions и judge-конфигураций не объединяются без явной маркировки.

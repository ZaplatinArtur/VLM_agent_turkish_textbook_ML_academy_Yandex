# Замеры профилей: база против дообученной

Отчёты `retrieve.evaluate` по двум эталонам: реальные задачи
(`data/eval/qrels_llm_all.jsonl`, 187 запросов) и синтетика
(`data/eval/synthetic_qrels.jsonl`, 300). Из них собраны таблицы в
`reports/tables/TABLE_*.md`.

Имя файла — `<эталон>-<профиль>.json`, где профиль:

| в имени | профиль |
|---|---|
| `ce` | `rrf_e5-small_bm25_cross-encoder` |
| `e5m3` | `rrf_e5-small_m3_bm25_cross-encoder` |
| `m3` | `rrf_m3_bm25_cross-encoder` |
| `m3-dense` | `m3` сам по себе, без RRF и кросс-энкодера |
| `minilm`, `bm25`, `e5small`, `e5base`, `qwen3` | одноимённые лёгкие профили |
| `e5small-bm25`, `e5base-bm25`, `e5small-m3-bm25`, `e5base-m3-bm25` | соответствующие `rrf_*` |
| `*-gate` | тот же профиль с LLM-гейтом |

Приписка `m3-dense` нужна из-за коллизии: `real-m3.json` занят профилем с
кросс-энкодером.

## `base/` и `tuned/`

Одни и те же профили без адаптера и с `data/models/bge-reranker-v2/chosen`.

**Приписка `-fp16` — кросс-энкодер в половинной точности**, замер 12 августа. Файлы без
приписки — прежние, fp32; оставлены, потому что из них считалась дельта для
гейтовых строк. В таблицах стоят fp16-числа: медиана 1524 → 382 мс, качество
совпало (hit@k и MRR точно, nDCG и recall — в пределах 0.1 пп).

**Все негейтовые прогоны сделаны по одному на карте.** Это не педантизм: при
четырёх параллельных процессах латентность раздувалась вчетверо (7128 мс против
1739) при неизменном до десятой доли качестве. Сравнивать «мс» можно только между
замерами одного захода.

Гейтовые прогоны шли при соседях на нулевой карте, их «мс» с базовыми
гейтовыми несравнима — качество это не затрагивает, оно детерминировано.

## `calibration/`

Порог детектора бесполезного поиска (`retrieve.confidence`) для
`rrf_e5-small_bm25_cross-encoder`: `threshold-base` без адаптера,
`threshold-tuned` с ним, оба одним заходом на одной карте. Считались по
`data/eval/eval_queries_tr.txt` против `eval_queries_ood_tr.txt` — заведомо чужих
корпусу запросов.

Итог: свои и чужие разделимы полностью в обоих случаях, плато порога у
дообученной 0.13–0.63, `CROSS_ENCODER_MIN_SCORE = 0.5` внутри. Менять не нужно.

    python -m retrieve.compare --systems <профиль> --reference none --calibrate \
        --index-root data/cache/index --output reports/CAL_<tag>.json

## `controls/`

Три замера, которыми доказано, что провал первой версии дообучения — не случайность:

* `no-adapter.json` — без адаптера воспроизводится ровно 78.1 hit@1, то есть
  пайплайн исправен и сравнение честное;
* `broken-labels-r16.json` — 62.6, не лучше r=32, значит дело не в ранге LoRA;
* `broken-labels-r32.json` — 63.6, тот самый провал на 15 пунктов.

## Почему в срезах реального эталона были прочерки

Срезы считаются из по-запросных метрик, а ранняя версия `retrieve.evaluate`
писала в файл одни средние. Тринадцать профилей, замеренных до этой правки, в
таблице по предметам показывали прочерки — при том что «Сумма» у них на месте.

Закрыто 12 августа перемером всех десяти лёгких профилей поодиночке на нулевой
карте, на обоих эталонах (`real-minilm.json`, `synth-minilm.json` и далее).
Двадцать прогонов заняли 15 минут: индексы лежат в `data/cache/index`, корпус
заново не кодируется. **Качество совпало с прежним до последнего знака во всех
двадцати** — заодно доказано, что кэш индекса воспроизводит старый прогон.

«Мс» на реальных задачах просела на 5–20% (старые числа снимались при двух
параллельных ветках), на синтетике выросла на 2–10%. Обе разницы внутри полосы,
которую мы объявили нечитаемой; смысл перемера в том, что колонка стала из одного
захода, а не в самих числах.

Три профиля с кросс-энкодером достроены без прогона, из `base/`: там лежит тот же
самый заход, что дал числа в таблице.

`backfill_per_query.py --replace` подставляет свежий замер целиком; без флага он
переносит только по-запросные метрики, а «мс» выбрасывает, если источник — другой
заход. Качество детерминировано и переносимо, время нет.

## Как пересобрать таблицы

    python scripts/backfill_per_query.py reports/tables/real_ranking_base.json \
        --from reports/measurements/base/real-ce.json reports/tables/real_recall.json ... \
        --output reports/tables/real_ranking_base.json
    python scripts/merge_tuned_reports.py reports/tables/real_ranking_base.json \
        reports/measurements/tuned/real-ce.json ... --output reports/tables/real_ranking_tuned.json
    python scripts/report_tables.py reports/tables/real_ranking_tuned.json --grid \
        --labels data/eval/real_subject_labels.jsonl --by предмет \
        --grid-metrics hit_rate_at_1 hit_rate_at_5 hit_rate_at_10 ndcg_at_10 mrr_at_10 recall_at_10 \
        --output reports/tables/TABLE_real_subject.md

`merge_tuned_reports.py` отказывается работать, если хоть одна старая метрика
разошлась с исходным файлом.

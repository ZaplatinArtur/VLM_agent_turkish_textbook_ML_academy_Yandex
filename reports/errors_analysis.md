# Анализ ошибок модели (B0 и B1-deep-routed, 298 задач)

Источник: `reports/errors_report.html` (генератор `mla_baseline/errors_report.py`,
метрика — exact-match для авто-задач, LLM-судья для остальных; 24 задачи без
валидного эталона исключены).

## Структура ошибок

Из 274 оцениваемых задач ошибка хотя бы одного условия — в **106**:

| Класс | n | Что это |
|---|---|---|
| Обе конфигурации ошиблись | 59 | устойчивые пробелы модели |
| — из них одинаковый неверный ответ | 27 | систематические ошибки (не шум) |
| Только B0 ошибся | 24 | преимущественно шум сэмплирования |
| Только B1dr ошибся | 23 | преимущественно шум сэмплирования |

Симметрия 24 vs 23 — ещё одно подтверждение паритета условий: односторонние
ошибки — это задачи «на грани», где решает бросок температуры 0.6.

## Не ошибки модели: артефакты данных и оценки (~12 из 106)

1. **Битые эталоны (2)**: `val_0063` — эталон «45756» (Excel-серийная дата);
   модель решает верно (куб 3×3×3, P(ровно 2 грани) = 12/27 = 4/9).
   `val_0196` — судья сам пишет «reference states no question exists».
2. **Кириллица в эталоне (1)**: `val_0165` — эталон «С» (кириллическая),
   модель отвечает латинской «C»; exact-match не совпадает, судья зачёл.
   → в `eval.match` стоит добавить маппинг кириллических букв-омоглифов.
3. **exact строже судьи (3)**: `val_0257` «1/2» vs эталон «50%» и т.п. —
   эквивалентные формы числа. → нормализация процентов/дробей в `eval.match`.
4. **JSON протёк в final_answer (7)**: модель кладёт весь JSON внутрь поля
   ответа (`{"reasoning": ...`). → харнес: детект и повторный парс вложенного
   JSON в `parse_solve_output`.
5. **Транскрипции-огрызки** (часть 72 мостовых эталонов): эталоны вида «a»,
   «h», «1» у многосоставных открытых задач (`val_0061`, `val_0163`,
   `val_0178`) — VL-транскрипция сняла подпункт, а не ответ. Судья к таким
   эталонам строг → занижение на «открытых точных». Ждёт человеческих эталонов
   или extract-validation-text от судейской команды.

## Настоящие устойчивые пробелы (57 задач, ядро — 27 с одинаковым ответом)

**Математика — 26 из 57.** Почти вся закрытая часть: модель считает, получает
уверенный, но неверный результат; обе конфигурации сходятся к одной букве
(`val_0073`, `val_0076`, `val_0243`, `val_0251`, `val_0274`, `val_0280`,
`val_0297`…). Роутинг тут не спасает — это предел вычислительной способности
9B на 32k-бюджете.

**Тонкое визуальное чтение — характерный кластер.** Разобранный пример
`val_0130` (физика): сопоставления «механика→мост, оптика→микроскоп,
электромагнетизм→МРТ» модель делает **верно**, но не может визуально
различить, какая из пяти стрелочных диаграмм в вариантах кодирует это
сопоставление — обе конфигурации выбирают одну и ту же неверную диаграмму
(та же картина в `val_0131`, `val_0132`). Аналогично `val_0022` (развёртка
куба с отражением). Это не пробел знаний и не ошибка счёта — это предел
пространственного восприятия 9B: стрелки, развёртки, геометрические позиции.
Поиск такие ошибки не лечит принципиально.

**Знаниевые предметы — по 3–6 ошибок на предмет** (биология 6, турецкий 5,
химия 5, история 3…): распределены тонко, без выраженного кластера; частично
закрываются поиском (см. предметные срезы в сводном отчёте), частично — предел
модели.

## Выводы

1. ~11% «ошибок» — не ошибки модели: чинится нормализацией eval (кириллица,
   проценты/дроби), парсером вложенного JSON и чисткой эталонов. Дешёвый
   прирост ~2–3 пп к измеряемому качеству без изменения модели.
2. Ядро реальных пробелов — математика (вычисления) и тонкое визуальное
   чтение диаграмм/развёрток. Оба класса не решаются поиском; первый частично
   отвечает на бюджет рассуждения, второй — нет (нужна модель крупнее или
   специализированный визуальный препроцессинг).
3. Односторонние ошибки (47 из 106) — margin-задачи: их распределение между
   условиями определяется сэмплированием, что согласуется с выводом о
   статистическом паритете B0 и B1dr.

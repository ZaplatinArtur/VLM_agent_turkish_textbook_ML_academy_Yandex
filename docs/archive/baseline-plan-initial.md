# Первоначальный план разработки бейзлайнов

> Исторический документ. Он фиксирует ранний план до интеграции OpenRouter,
> image-first checked RAG и текущего evaluation pipeline. Для запуска используйте
> [`../getting-started.md`](../getting-started.md), а актуальную архитектуру
> смотрите в [`../project-map.md`](../project-map.md).

## 1. Цель и место бейзлайнов в проекте

Итоговое сравнение — три условия на одном и том же наборе задач:

| Условие | Кто делает | Что внутри |
|---|---|---|
| B0 — «голая» модель | мы (бейзлайны) | один вызов VLM: «Реши» + картинка |
| B1 — модель + веб-поиск | мы (бейзлайны) | агент с единственным тулом web-search |
| Agent — RAG по учебникам + поиск | команда агента + команда ретрива | полный агент |

Бейзлайны нужны, чтобы показать вклад (а) поиска и (б) RAG по учебникам. Оценивает всё LLM-as-Judge (отдельный человек), поэтому наш главный продукт — не только код бейзлайнов, но и **единый формат результатов**, который судья сможет потреблять для всех трёх условий.

## 2. Принципы честного сравнения (зафиксировать до кода)

Согласовать со всей командой, иначе сравнение будет некорректным:

1. **Одна модель** во всех трёх условиях: Qwen 3.5 9B — обязательно **VL-вариант** (задачи приходят картинкой, текстовая версия модели их не прочитает; это первое, что нужно проверить). Один чекпоинт, один общий inference-эндпоинт (vLLM, OpenAI-совместимый API), одни sampling-параметры, зафиксированные в `config.py`.
2. **Один системный промпт-каркас** (роль «решаешь школьную задачу», требования к оформлению решения и финального ответа). Отличия между условиями — только в доступных тулах и инструкциях по их использованию.
3. **Один формат входа**: сообщение пользователя = текст «Реши» (тур. «Çöz») + условие задачи. Основной сценарий — условие приходит **картинкой** (фото/скрин, base64): предполагаем ленивого школьника. Текстовый вход тоже поддерживаем (условие строкой вместо изображения) — solver принимает и то и другое, но eval-набор строим преимущественно из картинок, т.к. именно этот сценарий проверяем. Никакого ручного OCR/переписывания условий картиночных задач. Язык промптов и решений — турецкий (гипотеза тестируется для турецкого рынка; решать турецкие задачи с ответом на другом языке — нерепрезентативно).
4. **Один формат выхода** (structured output): `{final_answer, solution_steps, confidence?}` — то, что парсит судья. Для 9B-модели строгий JSON надёжнее выбивать через guided decoding vLLM (`response_format` / `guided_json`), а не надеяться на промпт.
5. **Один фиксированный eval-набор задач**, прогоняемый всеми условиями. Сид/версия набора фиксируются.
6. **Одинаковые бюджеты**: лимит итераций агента, лимит вызовов поиска, max_tokens.

## 3. Контракты с командой (согласовать в первые дни)

### 3.1. Манифест датасета (вход)
```json
{
  "task_id": "math_7_015",
  "input_type": "image | text",        // основной сценарий — image
  "image_path": "data/images/math_7_015.png",  // null для текстовых задач
  "task_text": null,                   // условие строкой для input_type=text
  "subject": "математика",
  "grade": 7,
  "source": "ссылка/учебник",
  "reference_answer": "12 см²"   // если есть — судье сильно проще
}
```

### 3.2. Формат результата (выход, JSONL — вход для LLM-as-Judge)
```json
{
  "task_id": "math_7_015",
  "condition": "b0_no_tools | b1_search | agent_rag",
  "model": "qwen3.5-9b-vl",
  "prompt_version": "v1",
  "final_answer": "...",
  "solution_steps": "...",
  "raw_response": "...",
  "tool_calls": [{"tool": "web_search", "query": "...", "n_results": 5}],
  "usage": {"input_tokens": 0, "output_tokens": 0, "latency_s": 0.0},
  "error": null
}
```

### 3.3. Интерфейс тулов ретрива (для будущей интеграции)
Попросить у команды ретрива сигнатуру их тулов (например, `retrieve(query, subject, grade) -> list[Document]`) — бейзлайн B1 строим так, чтобы тул поиска подключался через тот же механизм (LangChain `@tool`), тогда агент = наш же каркас + их тулы.

### 3.4. Передача данных от команды ретрива
Парсингом источников (таблицы, диски, odevjet) занимается команда ретрива — мы данные не собираем, а получаем. Согласовать с ними формат выгрузки задач: картинки + метаданные (предмет, класс, источник, ответ, если извлекается). Наша часть — только отбор и сборка eval-манифеста (§3.1) из их выгрузки. Важно договориться о сроке первой выгрузки: eval-набор — блокер для этапов 5–6.

## 4. Архитектура кода

```
mla_baseline/
  config.py            # модель, лимиты, версии промптов
  prompts.py           # системные промпты (версионируются)
  schemas.py           # pydantic: TaskItem, SolveResult
  solvers/
    base.py            # интерфейс: solve(task: TaskItem) -> SolveResult
    b0_no_tools.py     # прямой вызов VLM
    b1_search.py       # LangGraph ReAct-агент с web_search
  tools/
    web_search.py      # обёртка поиска (Tavily / DuckDuckGo / нативный web search)
  data/
    manifest.jsonl     # eval-набор
    images/
  runner.py            # батч-прогон: manifest × solvers -> results/*.jsonl
  results/
```

- **Serving**: vLLM с Qwen 3.5 9B VL, поднятый как OpenAI-совместимый эндпоинт (`vllm serve ... --enable-auto-tool-choice --tool-call-parser hermes` — парсер тул-коллов для Qwen обязателен, иначе агент в B1 не заработает). Из LangChain подключаемся через `ChatOpenAI(base_url=..., api_key="EMPTY")`. Один эндпоинт на всю команду — это и есть гарантия «одной модели».
- **B0**: `llm.invoke([system, human(text+image)])` + guided JSON. Тривиально, но это опорная точка всего сравнения.
- **B1**: `langgraph.prebuilt.create_react_agent(llm, tools=[web_search])`, лимит итераций (например, 8) и лимит вызовов поиска (например, 5). Поиск, полностью open source: **SearXNG** (self-hosted метапоиск) — основной вариант; DuckDuckGo (`ddgs`) — быстрый старт без развёртывания, но это внешний сервис с рейт-лимитами. Поиск должен работать по турецким запросам — проверить на этапе smoke.
- **Runner**: последовательный/пул на N потоков (vLLM сам батчует конкурентные запросы — параллелизм даёт почти бесплатное ускорение), ретраи на сетевые ошибки, resume по task_id, кэширование готовых результатов, итог в JSONL.

## 5. Этапы и порядок работ

| Этап | Содержание | Результат |
|---|---|---|
| 0. Инфраструктура (день 1–2) | repo, `pyproject.toml`, зависимости (`langchain`, `langgraph`, `langchain-openai`, `pydantic`); поднять vLLM с Qwen 3.5 9B VL на GPU-машине, проверить vision-вход и tool calling через эндпоинт; поднять SearXNG (docker) | каркас запускается, модель отвечает на «Çöz + картинка» |
| 1. Контракты (день 1–2) | согласовать §3 с командой ретрива и судьёй | зафиксированные схемы |
| 2. Данные (день 2–4) | получить выгрузку задач от команды ретрива (§3.4); отобрать eval-набор (~50–100 задач, стратифицировано по предметам и классам), собрать `manifest.jsonl` + картинки; проверить качество сканов. Полезно: для 10–20 задач сделать текстовые «двойники» (то же условие строкой) — прогон image vs text разделяет ошибки «не прочитал картинку» и «не решил задачу». | 4. B1 (день 3–5) | тул поиска, ReAct-агент, лимиты, логирование tool_calls | рабочий B1 |

| 7. Интеграция (когда готовы тулы ретрива) | подключить их тулы в наш каркас как третье условие, финальный прогон всех трёх | таблица сравнения |

## 6. Разделение работы на двоих

Парсинг данных — у команды ретрива (§3.4), поэтому оба человека на бейзлайнах занимаются кодом и оценкой. Делить вертикально (каждый владеет своим бейзлайном целиком), с общей инфраструктурой у одного:

- **Человек 1 (я)**: vLLM-эндпоинт с Qwen 3.5 9B VL + каркас (`schemas`, `solvers/base`, `runner`, `config`) + B0 + формат результатов и связь с судьёй.
- **Человек 2**: SearXNG + B1 (тул поиска, агент) + сборка eval-манифеста из выгрузки ретрива (отбор, стратификация, текстовые «двойники») + связь с командой ретрива по формату выгрузки.

Точки синхронизации: контракты §3 (вместе, в начале), ревью промптов друг друга, совместный smoke-прогон.

Альтернатива, если человек 2 сильнее в агентной части: поменяться — я беру B1 и SearXNG, он — каркас, B0 и манифест.

## 7. Риски и что с ними делать

- **9B — маленькая модель, и это главный риск.** Слабее instruction following, ненадёжный tool calling, хуже математика. Последствия для нас: (а) строгий JSON — только через guided decoding vLLM, плюс запасной парсер в коде; (б) в B1 закладывать fallback «агент не вызвал ни одного тула / зациклился» — логировать это как отдельный исход, а не как ошибку прогона; (в) промпты держать короткими и простыми, без сложных многошаговых инструкций.
- **Турецкий язык.** Промпты, решения и поисковые запросы — на турецком. Проверить качество турецкого у Qwen 3.5 9B на первых 10 задачах до массовых прогонов; если модель сбивается на английский/китайский в решениях — фиксировать язык явной инструкцией и проверять в smoke.
- **VL-вариант и качество картинок.** Убедиться, что используется vision-чекпоинт и что он читает турецкий текст со сканов (OCR-способность на турецком — отдельная проверка). Плохие сканы отсеять при сборке eval-набора.
- **LLM-as-Judge на той же модели.** Если судья тоже будет Qwen 9B, он слабее задач, которые оценивает — это известная проблема. Передать коллеге по оценке: судью лучше делать на более крупной open-source модели (например, Qwen 72B / другой большой чекпоинт), это не нарушает чистоту эксперимента — судья не участвует в решении.
- **Нет эталонных ответов.** Если у задач нет ответов, судья оценивает только по решению — заранее спросить судью, нужен ли ему `reference_answer`, и собирать его где возможно.
- **GPU — общий ресурс.** Прогоны трёх условий и итерации промптов конкурируют за один эндпоинт; договориться о расписании больших прогонов, для отладки использовать под-набор из 10 задач.
- **Поиск нестабилен** (разные результаты в разные дни; у DuckDuckGo — рейт-лимиты). Логировать запросы и выдачу; финальные прогоны всех условий делать в близкие даты; предпочесть self-hosted SearXNG.
- **Дрейф промптов.** Любое изменение промпта = новая `prompt_version`; результаты разных версий не смешивать в одном сравнении.

## 8. Definition of Done

- `manifest.jsonl` (eval-набор) зафиксирован и согласован.
- B0 и B1 прогоняются одной командой (`python -m mla_baseline.runner --condition b1_search`) по всему набору без ручных вмешательств.
- Результаты в согласованном JSONL приняты человеком с LLM-as-Judge.
- Каркас позволяет подключить тулы ретрива без переписывания (агент = третий solver).

# История экспериментов

## Как читать статусы

| Статус | Значение |
|---|---|
| `baseline` | зафиксированный comparator, а не новая идея |
| `gold-blind dev` | inference не читал reference answer, но измерение сделано на знакомом development наборе |
| `dev-selected` | механика gold-blind, однако вариант выбран после сравнения на том же benchmark |
| `one-shot dev replay` | source wave заморожена до score и оценена один раз, но benchmark ранее изучался |
| `attribution failure` | число пересчитывается, но не измеряет механизм, указанный в названии |
| `post-hoc` | правила или подстановки созданы после просмотра исходов отдельных задач |
| `invalid generalization claim` | полезная forensic-диагностика или upper bound, не accuracy системы |
| `pending` | нет завершённого matched-judge отчёта; число не сообщается |

### Где в цепочке появилась 27B

Ранние no-tools, Active Crop и Visual Sketchpad ветки были построены на `Qwen/Qwen3.5-9B`. Но историческая source-native ladder продолжилась не от чистого 9B solver. Её корневым anchor стал результат meta-verifier/repair: 272 строки были ответами `Qwen/Qwen3.5-27B`, ещё две строки сохранили 9B-ответ после fail-closed ошибки генерации.

Дальше OGM source, direct-PDF и V1–V7 копировали строку anchor и заменяли ответ только при принятом source certificate. Поэтому source-часть сама по себе не требует 27B, но итоговые V6/V7 solver files сохраняют 27B answers на всех строках без override. Это важная граница атрибуции: historical V6/V7 — не all-9B системы.

Отдельный matched direct experiment не показал преимущества большей модели на этом benchmark при текущем judge-v2:

| Direct comparator | Current judge-v2 | Model lineage | Pairwise с 9B |
|---|---:|---|---|
| Clean no-tools 9B | 193/274 = 0,7044 | 274 строки 9B | reference comparator |
| Stronger-27B direct | 190/274 = 0,6934 | 262 строки 27B + 12 fail-closed 9B | 19 строк только 27B correct, 22 строки только 9B correct |

Это полезная matched-проверка, но не идеальная causal ablation размера модели: в 27B arm есть 12 9B fallbacks, а исторический runtime ранней 9B генерации закреплён слабее, чем answer vector и prompt. Корректный вывод узкий: на этих сохранённых outputs и едином judge-v2 27B direct не улучшил 9B direct.

После аудита эти ветки были исключены из production claim. Это одна из важнейших частей работы: завышенная цифра была обнаружена не внешним ревьюером, а внутри проекта.

### Что означают номера версий

Это не новые веса модели. Версия означает новую замороженную волну source records, adapters и certificates.

- V2 научилась восстанавливать верхний номер задания из layout только при строгой геометрии.

- V6 добавила source-native Sociology и Biology, включая all-page SIFT/RANSAC visual binding.

### Почему V6 и V7 надо показывать отдельно

V6 изменил четыре solver answers и получил четыре clean fixes. V7 дал +4 по метрике, но solver answer изменился только на `val_0196`; ещё три строки получили другой evaluator verdict при неизменном ответе. Следовательно:

- **V6 0,8686** — основной solver/source результат;
- **V7 0,8832** — полный system result нового source-adjudicated протокола.

## Диагностика математической метрики

Frozen score математики у V6/V7 — 112/139 = 0,8058. Отдельный ручной audit раннего anchor 108/139 нашёл 11 вероятных false negatives и одну задачу без необходимого рисунка. Диагностически это давало бы 119/139 = 0,8561 либо 108/127 = 0,8504 после исключения спорных строк.

Эти числа **не заменяют frozen metric**: предложения relabel не прошли независимую двойную проверку. На постере основной результат остаётся 112/139.

## Что в итоге оказалось полезным

1. Сильный default важнее большого числа слабых candidates.
2. Router должен использовать наблюдаемое содержание, а не идентичность benchmark строки.
3. Retrieval relevance недостаточно: нужна связь `source → page → marker → key cell → answer`.
4. Tool полезен только как proof producer с проверенными входами.
5. Visual branch лучше использовать для доказательства идентичности страницы, а не как ещё один генератор ответа.
6. Abstain и сохранение anchor — полноценный правильный исход системы.
7. Отдельная проверка evaluator необходима: модель-судья тоже является источником ошибок.

## Этап 9. Перенос source ladder обратно на 9B

Чтобы отделить вклад source certificates от historical 27B-derived anchor, были построены две offline-композиции на тех же 274 строках:

1. clean rebase от исходного no-tools 9B answer vector;
2. tuned rebase от all-9B Active Crop anchor.

Старые V1–V7 solver files нельзя просто переименовать в 9B. Их profiles, resolver manifests, certificates и composition decisions hash-bound к старому 27B-derived anchor, а решения composer содержат старый `anchor_answer`. Поэтому новый replay заново связал проверенные source candidates с 9B anchor, не копируя ни один 27B answer и не используя gold, score или outcome для routing.

Active Crop выбран как измеренный all-9B development anchor, но это post-hoc выбор после просмотра benchmark.

# Оценка, утечки и воспроизводимость

## Три разных вида результата

### 1. Development replay

Модель и правила запускаются без reference answer на входе, но сам набор уже использовался при выборе идей. Все текущие 274-задачные результаты относятся к этой категории.

Это честный ответ на вопрос:

> Что делает зафиксированный pipeline на знакомом development benchmark, если во время конкретного inference он не видит gold?

Это не ответ на вопрос:

> Какова ожидаемая точность на новой книге?

### 2. One-shot development replay

Код, source records, thresholds и команда score заморожены до открытия результата конкретной source wave. V4–V7 использовали этот более строгий процесс.

One-shot защищает от rollback и cherry-picking внутри волны, но не отменяет предыдущего знакомства с benchmark.

### 3. Holdout

Задачи или книги не используются ни при выборе pipeline, ни при настройке thresholds, ни при error analysis. Такого результата для V7 пока нет.

## Почему `gold-blind` не равно `unbiased`

Gold-blind inference означает, что solver/resolver не читает reference answer. Но если разработчик проверил 30 вариантов на одном наборе и оставил лучший, метрика становится dev-selected. Это нормальный процесс разработки, если статус указан прямо.

Поэтому 205/274 для V2.1 + repair назывался `gold-blind, dev-selected`, а не holdout. V6/V7 усилили process discipline через pre-score freeze, но benchmark всё равно оставался ранее изученным.

## Что именно было утечкой в ранних ветках

Само наличие `task_id` не является утечкой: он нужен для alignment. Утечка начинается, когда identity строки выбирает ответ или verdict.

Выявленные запрещённые механизмы:

- task-ID keyed answer override;
- image-SHA keyed answer map;
- список ошибок benchmark как routing table;
- ручное изменение `strict_correct` у выбранных image rows;
- post-hoc threshold после просмотра результата;
- использование judge outcome как inference feature.

Именно такие механизмы присутствовали в headroom-ветках 0,7664, 0,8321 и 0,9599. Они сохранены для аудита, но не должны импортироваться в production package.

## Разрешённые и запрещённые признаки

| Разрешено | Запрещено |
|---|---|
| текст/изображение текущей задачи | benchmark row number |
| subject/task/modality prediction | task ID как answer selector |
| OCR span, bbox и confidence | image SHA как ключ готового ответа |
| видимый printed marker | reference answer и acceptable answers |
| source identity, PDF SHA, page | judge correctness/verdict |
| retrieval score и winner margin | список ранее ошибочных строк |
| формула, units и tool trace | outcome-informed threshold |
| profile/version/runtime hashes | aggregate score во время generation |

## V6 и V7: разная семантика метрики

### V6

V6 изменил четыре solver rows относительно V5. Все четыре стали правильными. Старый контур оценки остался прежним. Поэтому V6 — наиболее удобная цифра для сравнения способности solver/source pipeline: **238/274 = 0,8686**.

### V7

V7 изменил correctness четырёх строк, но только на одной изменился solver answer. На трёх неизменный ответ был переоценён exact official-source certificate вместо opaque VLM judge.

Корректная запись:

```text
V6 solver/source result:           238/274 = 0.8686
новый подтверждённый solver answer:                  +1
source-backed evaluator corrections:                 +3
V7 source-adjudicated result:       242/274 = 0.8832
```

Некорректная запись:

```text
V7 научил модель решать ещё четыре задачи.
```

## Judge lineage

Benchmark использует 177 deterministic rows и 97 image-judge rows. Поэтому итог зависит не только от solver, но и от протокола оценки.

Historical no-tools 191/274 и matched re-judged no-tools 193/274 происходят из разных judge lineages. Разница `+2` не является улучшением модели. Аналогично V7 меняет evaluator для трёх source-certified image rows. Любое сравнение должно указывать lineage и механизм изменения.

## Math metric audit

Ручной read-only audit обнаружил 11 вероятных false negatives и одну задачу без необходимого рисунка. Диагностические числа 119/139 или 108/127 нельзя смешивать с frozen score:

- frozen result сохраняет исходную разметку;
- corrected result допускается только после независимой повторной проверки и versioned relabel manifest;
- pipeline нельзя настраивать так, чтобы он повторял заведомо ошибочный key;
- на защите надо показывать оба слоя: immutable benchmark score и отдельный annotation-quality audit.

## Что уже воспроизводимо

- benchmark связан SHA-256;
- score reports содержат hashes solver, judge и scorer;
- V6 profile/index/resolver/composition имеют SHA bindings;
- V6 code и artifacts были сверены с remote commit до score;
- V7 зафиксировал candidate count, output paths, scorer command и atomic attempt marker;
- V7 не имел same-wave retry или retuning;
- source resolver использует task ID только для alignment;
- V6 visual artifact был пересобран в свежем subprocess и совпал byte-for-byte.

## Что пока не воспроизводимо из чистого клона

Локальный V6 handoff прямо фиксирует:

- 11 официальных PDF не хранятся в Git;
- общий объём внешних PDF около 499,48 MiB;
- требуются pinned Python/OpenCV/NumPy/Poppler bytes;
- generated manifests содержат абсолютные пути;
- fresh same-workspace replay возможен;
- location-independent fresh-clone replay не доказан.

Правильная формулировка: **artifact-bound reproducibility в исходном workspace**, а не полностью герметичная воспроизводимость.

## Минимальный clean-room protocol

1. Зафиксировать commit, profile и список разрешённых source documents.
2. Скачать PDF из manifest и проверить каждый SHA-256.
3. Создать новое окружение из lock-файла или контейнера.
4. Пересобрать рендеры, parser output, source index и visual features.
5. Не копировать serialized manifests с абсолютными путями.
6. Сравнить semantic content и hashes заново созданных artifacts.
7. Запустить generation без reference/score mount.
8. Только после завершения generation подключить evaluator.
9. Сохранить stdout/stderr, resolved config, runtime versions и wall-clock metrics.
10. Проверить, что clean output даёт тот же answer vector до открытия aggregate score.

## Как честно сделать набор из 80 новых задач

Если задачи берутся из уже имеющихся учебников, возможны два разных протокола.

### Task-disjoint, in-corpus holdout

- 80 ранее не просмотренных заданий;
- книги могут совпадать с индексом;
- страницы задач и ответы не участвовали в ручной настройке adapters;
- source corpus разрешён, потому что система именно по нему и должна искать;
- результат проверяет перенос на новые задания внутри известных book families.

Такой тест полезен, но не доказывает перенос на новые книги.

### Book/edition-disjoint holdout

- book/edition families не пересекаются с dev и calibration;
- новые книги добавляются автоматическим ingestion без ручного просмотра outcomes;
- thresholds заморожены заранее;
- это более сильная проверка generalization.

Для текущей задачи 80 task-disjoint in-corpus примеров уже существенно сильнее повторного score на 274, если список действительно скрыт до freeze. На постере его надо подписывать именно так.

## Freeze checklist перед 80-task run

- [ ] список 80 `task_id`/source rows создан независимым скриптом и sealed;
- [ ] нет пересечения с 274 development rows по exact/near-duplicate image/text hash;
- [ ] зафиксированы book/edition overlaps;
- [ ] commit и dirty-tree diff сохранены;
- [ ] model/checkpoint/prompt/runtime зафиксированы;
- [ ] source manifest и PDF hashes зафиксированы;
- [ ] router thresholds и certificate policy не меняются после запуска;
- [ ] generation окружение не имеет доступа к references;
- [ ] failures остаются в denominator;
- [ ] score открывается один раз;
- [ ] после score допускается только error analysis, не повтор того же заявленного run.

## Какие метрики показать кроме accuracy

- full-denominator accuracy;
- Math/non-math и subject slices;
- deterministic/image-source slices;
- solver failures и missing answers;
- source-certificate coverage;
- число `confirmed equal`, `override`, `abstain`;
- fixes/regressions относительно anchor;
- exact source round-trip success;
- p50/p95 end-to-end latency;
- model calls, tokens и cache hit rate;
- book-macro accuracy для нескольких book families;
- bootstrap interval, кластеризованный по книге, когда появится настоящий holdout.
